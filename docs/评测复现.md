# 评测复现指南

这份文档说明 `backend/results/` 下每个数字是**哪个脚本、什么数据、什么口径**跑出来的，以及别人拿到仓库后怎么自己跑一遍。

- 最近一次完整重跑：2026-11-15（检索链路 + 端到端）
- 运行环境：Windows 10 / Python 3.12 / Neo4j 5.26-community（本机实例，heap 1G、pagecache 512m）/ 单机
- 模型：embedding `text-embedding-v3`（1024 维，OpenAI 兼容接口）；规划与回答模型见 `backend/.env` 的 `PLANNER_MODEL_NAME` / `OPENAI_MODEL_NAME`

## 1. 环境准备

### 1.1 依赖

评测脚本比服务端多两个依赖：`pandas`、`pyarrow`（读 parquet）。它们放在独立的 `eval` 可选组里，不装也能正常启动服务：

```bash
cd backend
uv sync --extra eval          # 服务 + 评测
# 或者只装评测所需：uv sync --extra eval --no-group parsers
```

`parsers` 组是 `unstructured[all-docs]`（含 torch/CUDA，数 GB）。评测只用纯文本 parquet，**不需要装 parsers**。

### 1.2 只启动 Neo4j

检索与图谱评测只读 Neo4j，MySQL / Redis 不用起：

```bash
docker compose up -d neo4j
```

非 Docker 环境（本机实测）：Neo4j 5.26 + JDK 21，`bolt://127.0.0.1:7687`，账号密码在 `backend/.env` 的 `NEO4J_USER` / `NEO4J_PASSWORD`。

如果 `bin\neo4j.bat start` 报 `已添加了具有相同键的项`（PowerShell 5.1 + 中文 locale 下该管理脚本的已知问题），可以直接用 java 起，绕开 ps1：

```bash
# Git Bash，NEO4J_HOME 换成自己的解压目录
NEO4J_HOME=/d/ragnotebook-runtime/neo4j/extracted/neo4j-community-5.26.30
JAVA=/d/ragnotebook-runtime/jdk/jdk-21.0.2/bin/java.exe
cd "$NEO4J_HOME" && "$JAVA" -cp "lib/*;plugins/*" \
  --add-opens=java.base/java.nio=ALL-UNNAMED \
  --add-opens=java.base/java.io=ALL-UNNAMED \
  --add-opens=java.base/sun.nio.ch=ALL-UNNAMED \
  --add-opens=java.base/java.lang=ALL-UNNAMED \
  --add-opens=java.base/java.util=ALL-UNNAMED \
  -XX:+UseG1GC -Dfile.encoding=UTF-8 \
  org.neo4j.server.CommunityEntryPoint \
  --home-dir="$NEO4J_HOME" --config-dir="$NEO4J_HOME/conf"
```

启动后看 `logs/neo4j.log`，出现 `Started.` 与 `Bolt enabled on 127.0.0.1:7687` 即可。

### 1.3 API Key

`backend/.env` 至少要有：

```
OPENAI_BASE_URL=...
OPENAI_API_KEY=...
OPENAI_MODEL_NAME=...        # 端到端评测的裁判与回答模型
```

embedding 通道按 `EMBED_* → OPENAI_*` 回落；不配 `EMBED_*` 时用 `OPENAI_*` 的通道 + 默认模型 `text-embedding-v3`。

## 2. 检索评测（recall / MRR / p95 的来源）

### 2.1 数据集

`mteb/duretrieval`（中文检索数据集，DuReader-检索版），从 ModelScope 直链下载：

| 文件 | 规模 | 内容 |
|---|---|---|
| `corpus.parquet` | 100001 篇 | 文档正文 + 标题，平均 331 字 |
| `queries.parquet` | 2000 条 | 中文问题 |
| `qrels.parquet` | 9839 条 | query→doc 的相关性标注（二元） |

脚本首次运行会自动下载到 `backend/data/eval/duretrieval/`（约 65MB）。走 ModelScope 而不是 HuggingFace，因为 HF 在当前网络不可达。

### 2.2 抽样：seed 固定即口径固定

```bash
python scripts/eval_ingest.py --n-query 500 --n-doc 20000 --seed 42 --clean --concurrency 8
```

- 500 条 query 用 `random.Random(42).sample` 抽；
- 相关文档**全量保留**，再随机抽负例把总量补到 20000 篇；
- 抽样结果写入 `results/eval_retrieval/manifest.json`（query_ids / relevant_docs / doc_ids）。

**可复现性已验证**（2026-11-15）：用同样参数重跑 `sample()`，得到的 500 条 query 与 20000 个 doc_id 与 2026-10-12 的 manifest **完全一致**，集合差集为 0。所以两次评测是同一份数据、同一套 ground truth，结果可直接对比。

### 2.3 入库

| 项 | 值 | 出处 |
|---|---|---|
| 切片 | chunk_size 1000、overlap 20 | `app/config/document.yaml:5-6` |
| 嵌入 | `text-embedding-v3`，1024 维 | `.env` / `EmbedModelFactory` |
| 隔离 | 固定 `user_id=eval-duretrieval` | `--user-id` 默认值 |
| 写入 | `MERGE (c:Chunk {id, user_id})`，`id = doc:{doc_id}:{chunk_index}` | `neo4j_graph_store.upsert_chunks` |

`--clean` 只清 `eval-duretrieval` 这个用户的文档，不碰真实数据。

实测（2026-11-15，并发 8）：20000 篇 → 21359 个 chunk，**约 14 分钟**。embedding 约 4.3M token，按 text-embedding-v3 单价估算 **2~3 元**。

> 脚本原先逐篇调 `upsert_chunks`（每篇 2 次事务），2 万篇时事务提交成为瓶颈（实测约 0.9s/篇、需数小时）。现改为「先并发切分+嵌入，再按批一次 UNWIND 写入」，语义不变（同样是复合键 MERGE 幂等覆盖），速度提升一个量级。

### 2.4 跑分

```bash
python scripts/eval_recall.py --limit 100 --warmup 1
```

走的是**真实检索原语**，不是另写一套评测逻辑：

- `EmbedModelFactory().generator().embed_query(q)` 得到查询向量；
- `Neo4jGraphStore.search_chunks(user_id, emb, q, kinds=["doc"], limit=100)` —— 内部是向量 + 全文两路各取 `2×limit` 候选，按 RRF（k=60）融合排序（`neo4j_graph_store.py:674-726`）；
- 返回的是 chunk，按 `source_id` 去重回文档级排序，再对齐 qrels 算指标；
- `--warmup 1` 先跑一条不计时的占位 query，避免首次调用把连接池/JIT 的开销算进 p95。

### 2.5 指标定义

| 指标 | 定义 |
|---|---|
| recall@k | top-k 中命中的相关文档数 / 该 query 的相关文档总数 |
| hit@k | top-k 中是否至少命中一条相关文档 |
| MRR | 首个相关文档排名倒数（`1/rank`），无命中记 0 |
| nDCG@10 | 二元相关下的标准排序质量 |
| MAP | 平均精度，分母为该 query 的相关文档总数，`--limit` 截断 |
| 延迟 | 单 query 从发起检索到拿到 top-k，含 embedding 调用 |

### 2.6 结果（2026-11-15 重跑）

主表取第二次运行（`--warmup 3`，机器已稳定）：

| 指标 | 值 |
|---|---|
| recall@1 | 0.2660 |
| recall@3 | 0.5626 |
| recall@5 | **0.7286** |
| recall@10 | 0.8682 |
| hit@1 | 0.9180 |
| hit@3 | 0.9500 |
| hit@5 | 0.9580 |
| hit@10 | 0.9760 |
| MRR | **0.9383** |
| nDCG@10 | 0.8649 |
| MAP | 0.8199 |
| 延迟 p50 | 245.3 ms |
| 延迟 p90 | 343.9 ms |
| 延迟 p95 | **378.9 ms** |
| 延迟 mean | 258.9 ms |
| 延迟 max | 564.5 ms |

与 2026-10-12 那次对比：

| 指标 | 2026-10-12 | 2026-11-15 | 差异 |
|---|---|---|---|
| recall@5 | 0.7207 | 0.7286 | +0.008 |
| MRR | 0.9384 | 0.9383 | ≈ 0 |
| nDCG@10 | 0.8636 | 0.8649 | +0.001 |
| p50 | 259.6 ms | 245.3 ms | -14 ms |
| p95 | 321.1 ms | 378.9 ms | +58 ms |

质量指标稳定（差异都在 1 个点内），**延迟 p95 波动明显**：同一天连跑两次分别是 435.2 ms 和 378.9 ms，旧报告是 321.1 ms。p95 受 embedding 服务抖动和本机负载影响，属于环境噪声，不是检索逻辑变化。

> 结论：引用延迟时写「p50 约 0.25 s、p95 在 0.32~0.44 s 之间波动」，不要写死某一个 p95 数值。

### 2.7 口径边界（被追问时要说清）

1. **是通用中文语料，不是个人笔记**。DuRetrieval 是新闻/百科类长文，笔记更短、更口语、更多自造缩写，实际召回未必有这个水平。这份数据证明的是"检索链路本身不退化"，不是"在你的笔记上 recall 0.72"。
2. **文档级指标**。产品展示的是文档/笔记粒度，所以按 doc 算；chunk 级 recall 会更低。
3. **主链路没有 rerank**。RRF 之后直接进证据组装，`/chat/reorder` 是另一个独立接口，不在 agentic_rag 链路里。这里的 0.72 是纯 RRF 成绩。
4. **p95 含 embedding 网络调用**，不是纯图数据库查询耗时。embedding 服务抖动会直接反映在 p95 上。

## 3. 端到端评测（答案质量 + 延迟）

```bash
python scripts/eval_end2end.py --n-samples 20 --seed 7
```

流程：从已入库语料取正文 → LLM 生成 (问题, 参考答案) → 跑真实 `AgenticRagService.run()` → 用产品同款 system prompt 生成回答 → LLM 裁判打 faithfulness / correctness（1-5 分）。

**口径提醒**：题目由源正文生成，检索必然命中，所以这套评测衡量的是**答案质量、忠实度、延迟**，**不衡量检索难度**。检索难度看第 2 节。

### 结果（2026-11-15 重跑）

| 指标 | 2026-10-12 | 2026-11-15 | 变化 |
|---|---|---|---|
| 忠实度 | 4.35 | 4.75 | +0.40 |
| 正确性 | 3.75 | 4.50 | +0.75 |
| 忠实度 ≥4 占比 | 0.80 | 0.95 | +0.15 |
| 正确性 ≥4 占比 | 0.65 | 0.90 | +0.25 |
| 平均证据条数 | 6.10 | 5.00 | -1.10 |
| 管线耗时（规划+检索+可答性） | 30.2 s | 4.9 s | **-84%** |
| 回答首 token | 7.0 s | 4.0 s | -3.0 s |
| 用户感知首 token | 37.2 s | 8.9 s | **-76%** |

管线耗时从 30 秒降到 4.9 秒，原因不是"机器变快了"，而是 planner 拆出了独立小模型通道（`PLANNER_*`）：单次规划从复用主回答模型时的 ~30 秒降到 1.2~2.0 秒。逐条日志可以直接核对：

```
【RAG耗时】total=4780ms planner=1367ms retrieval=15ms evaluator=3398ms web=0ms used_web=False fused=5
```

注意两件事：

1. **现在管线里最贵的是 evaluator（3.4~3.7 s），不是 planner**。要继续压延迟，下一个该动的是可答性判断这一步。
2. **质量分上升不代表系统真的变强**。题目由源正文生成、检索必然命中，样本只有 20 条，分数天生偏高。这套评测的用途是"回归检测 + 延迟观测"，不是对外宣称"忠实度 4.75"。

被问到延迟时：planner 单步 1~2 秒、管线 5 秒、用户感知首 token 约 9 秒。简历里写的"2~4 秒"是旧配置的规划耗时，当前实测更快，但**不要把它说成端到端**。

## 4. 图谱评测

### 4.1 建图

```bash
python scripts/eval_build_graph.py --n-docs 200 --concurrency 8
```

从 manifest 取文档 → LLM 抽实体关系 → 顺序写 `upsert_entity` / `create_relation` / MENTIONS 边。固定 `eval-graph` 用户隔离。这一步是**成本最高**的评测（每条文档一次 LLM 抽取）。

### 4.2 实体检索

```bash
python scripts/eval_graph_entity_recall_v2.py --n 40 --top-k 10
```

从图中取实体造问题，测真实 `search_graph` 路径（LLM 抽查询实体 → 匹配图中实体 → 带出提及 chunk）。

结果（2026-10-12）：实体 hit@1/3/5/10 全是 0.90，未召回 6 条，检索 p50 **13.9 秒**。

两点必须主动说明：

1. hit@k 四个值一样，是因为 `search_graph` 一次返回实体列表，只要命中就落在同一位置，k 在这条路径上不敏感——这个指标只能说明"能不能找到"，不能说明排序质量。
2. 13.9 秒是"LLM 抽实体"这一步的代价，不是图查询慢。

### 4.3 多跳增量

```bash
python scripts/eval_graph_multihop.py --n 20 --top-k 5
```

从图中抽 2 跳路径 `a -r1-> b -r2-> c`，构造问题问 a 与 c 如何关联，对比图路径与纯文本路径。

结果（2026-10-12，15 条有效样本）：中间实体覆盖 0.867 vs 0.600，但**端到端答案正确率 0.40 vs 0.40，增量为 0**；图路径检索均值 43 秒。

诚实的结论是：**当前实现的图检索（实体匹配 + chunk 提及，不做邻居扩展）在证据覆盖上有优势，但没有转化为答案质量提升，而且延迟高一个量级**。这一条不要包装成"图检索提升回答效果"。

## 5. 已知限制

| 限制 | 影响 | 是否已处理 |
|---|---|---|
| 图谱实体 hit@k 对 k 不敏感 | 指标区分度低 | 未处理，解读时说明 |
| 多跳答案正确率无增量 | 图检索价值未被证明 | 未处理，如实记录 |
| 端到端 20 样本 | 置信区间宽 | 可加大 `--n-samples`，成本线性上升 |
| 端到端首 token 8.9 s | 不适合实时对话 | planner 已拆小模型（1~2 s）；下一个瓶颈是 evaluator（3.5 s） |
| 主链路无 rerank | 精度上限受限 | `/chat/reorder` 已存在，未接入 agentic_rag |
| 评测为单机、单用户 | 未测并发与多租户 | 未处理 |

## 6. 一键复现清单

```bash
cd backend
uv sync --extra eval
docker compose up -d neo4j          # 或本机 Neo4j 5.26

# 1) 建检索语料（约 14 分钟、2~3 元 embedding）
python scripts/eval_ingest.py --n-query 500 --n-doc 20000 --seed 42 --clean --concurrency 8

# 2) 检索指标（约 3 分钟）
python scripts/eval_recall.py --limit 100 --warmup 1

# 3) 端到端（约 7 分钟，需要 LLM Key）
python scripts/eval_end2end.py --n-samples 20 --seed 7

# 4) 图谱（建图最贵，可选）
python scripts/eval_build_graph.py --n-docs 200 --concurrency 8
python scripts/eval_graph_entity_recall_v2.py --n 40 --top-k 10
python scripts/eval_graph_multihop.py --n 20 --top-k 5
```

跑完对比 `results/*/report.md` 的数值；浮动在 1~3 个点以内属正常（embedding 服务、数据版本、并发都会影响）。
